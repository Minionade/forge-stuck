# Forge 1.20.1 Compatibility Inventory

Last scanned: 2026-10-18

This inventory tracks bytecode references in the supplied Minecraft 1.20.1 Forge mod jars. The detailed, deduplicated call and field reference list is in [forge-1.20.1-call-inventory.tsv](forge-1.20.1-call-inventory.tsv). Update its status as compatibility patches are implemented and verified.

## Scope and method

Scanned only the 13 jars whose filenames identify Minecraft 1.20.1, plus Jar-in-Jar classes embedded in those jars (including `thermal_core` inside Thermal Foundation). NeoForge 1.21.1 jars were excluded.

The scan records bytecode method invocations, field accesses, and method/field handles whose symbolic owner begins with `net.minecraftforge`. It compares each owner and member against the current `ForgeOwnerMappings` table. It does not yet cover Forge-added methods invoked with Minecraft owners, descriptor-only references, reflection/string-based lookups, mixin targets, or resource/config references; those require follow-up passes before this can be considered an exhaustive migration audit.

Status meanings:

- `PATCHED`: the current owner/member remap table has a supported mapping. This confirms a transformer mapping exists, not that the corresponding behavior has been exercised in-game.
- `KNOWN_GAP`: the owner is mapped, but this member is not in its supported-member set. Existing transformation may leave the owner unmapped or replace the call with a runtime failure.
- `UNMAPPED`: no owner mapping was found. Verify whether the API still exists unchanged on NeoForge; add a compatibility patch when it does not.

The TSV contains **1,173 unique signatures** across the scanned jars: **1,119 patched**, **44 known gaps**, and **10 unmapped**. Their 9,443 bytecode references are distributed as 9,297 patched, 82 known-gap, and 64 unmapped references (98.5% patched). These are static bytecode-reference counts, not a claim that every reference executes at runtime.

## Remaining unmapped work

The 10 remaining unmapped signatures (64 bytecode references) include the conditional-recipe builders and strict-NBT ingredient helpers (7 signatures / 47 references), legacy entity-spawn packet creation (1 / 15), and projectile impact results and registry mutability (2 / 2). Ingredient serializer ID lookup is now adapted, but the remaining `CraftingHelper` parsing helpers and strict-NBT constructor/serializer are not. Strict-NBT's 1.20.1 item-tag payload cannot be mapped losslessly to 1.21.1 data components without a registry-aware codec. The single-variant conditional advancement builder used by TConstruct is supported; multi-variant conditional advancements fail explicitly, and the multiple-variant `ConditionalRecipe` builder remains unmapped. The supplied TConstruct code builds multiple condition-specific recipes under one ID and relies on Forge selecting the first passing variant. NeoForge 1.21.1 `RecipeOutput.withConditions` only adds conditions to an individual output and has no equivalent first-match recipe wrapper; moreover, the legacy builder accepts `Consumer<FinishedRecipe>`, while `FinishedRecipe` no longer exists in the target API. Keep those recipe-builder signatures unmapped rather than emitting duplicate recipe IDs or pretending the old consumer can be adapted. Several TConstruct entity call sites also implement Forge's additional-spawn-data interface, so a plain `ClientboundAddEntityPacket` would lose custom spawn data; leave `NetworkHooks.getEntitySpawningPacket` unmapped until a packet-equivalent adaptation is verified. Forge's `ProjectileImpactEvent.ImpactResult` distinguishes `SKIP_ENTITY` from cancellation and other impact outcomes, while NeoForge removed the result enum; do not alias the field or setter to cancellation without proving equivalent projectile behavior. `ForgeRegistry.unfreeze()` changes registry mutability, and NeoForge does not expose an equivalent lifecycle operation, so leave it unmapped rather than replacing it with a no-op.

The tier-drop predicate now uses the 1.21.1 tier's incorrect-block tag. `TierSortingRegistry.byName`, `getName`, and `getSortedTiers` are known gaps because the target API no longer maintains the Forge tier-name/order registry. The mapped GUI overlay tokens preserve identity for the three referenced vanilla layers; unsupported overlay event constructors, windows, and partial-tick access remain known gaps.

`ForgeHooks.onBlockBreakEvent` is a known gap rather than a safe alias: NeoForge's `BlockEvent.BreakEvent` preserves cancellation but has no Forge-compatible experience-to-drop result.

## Known-gap implementation plan

1. **Capabilities (highest impact):** type/token wrappers and the standard Forge capability constants are mapped, but generic provider lookup and registration remain incomplete. Trace each capability use to its item, block, or entity capability, then introduce typed query/provider adapters and lifecycle-correct registration only where the target event can be reached. Keep unsupported generic registration explicit. Validate with item, fluid, and energy capability provider/query tests across both present and absent results.
2. **Crafting and datapack compatibility:** the supplied single-variant conditional advancement builder is mapped to the advancement conditional codec, and ingredient serializer IDs resolve through the legacy registration table. Keep multi-variant conditional recipes unmapped unless a first-match equivalent and the removed `FinishedRecipe` consumer contract can be demonstrated. Adapt the remaining `CraftingHelper` parsing and strict-NBT ingredient serialization only when 1.21.1 data components and registry-aware codecs can preserve behavior; do not treat parse-only mappings as complete.
3. **Rendering and GUI:** separate legacy overlay identifiers/events from NeoForge GUI layers, adapt only the layer identities that have equivalent ordering/visibility, then address the changed quad-baking pipeline and sprite-mask geometry. Use transformer tests plus a client render smoke test; leave conversions unsupported where the old behavior cannot be represented.
4. **Runtime and registry lifecycle:** reverse-tag lookup now uses the registry's holder sets and preserves empty-tag behavior; the global-loot and sprite-source data-provider constructors use the built-in registry lookup provider. Validate that legacy brewing calls occur before NeoForge's registration event; and keep registry unfreeze operations explicit rather than creating success-shaped no-ops.
5. **Entity networking and closure:** use NeoForge's complex-spawn path for entities implementing the legacy additional-spawn-data interface; do not replace Forge's spawn packet with a vanilla packet that omits that payload. After each cluster, update the TSV and per-jar counts, run targeted transformer/behavior tests, then run the full suite and a transformed-jar startup smoke test.

## Updating the inventory

When adding or correcting compatibility, update the matching TSV rows from `UNMAPPED` or `KNOWN_GAP` to `PATCHED` only after the transformer mapping and relevant regression coverage are in place. Keep bytecode-reference totals and affected jar names intact. If the supplied mod jars change, rescan the 1.20.1 jars and refresh both this overview and the TSV; do not include NeoForge-native 1.21.1 jars.
